# 个人历史完整分页

## 问题

`GET /events/{userId}` 原先只执行一次 DynamoDB `Query`。当用户记录超过单次查询的 1 MB 上限时，接口忽略 `LastEvaluatedKey`，而个人仪表板和事件管理页会把这一页记录当成全部历史，用于数量、图表、筛选和搜索。

## 读取协议

`getVoiceEvents` 现在持续使用 `ExclusiveStartKey` 查询，直到响应不再包含 `LastEvaluatedKey`。即使某一页 `Items` 为空，只要仍有游标就会继续读取。全部页面读取成功后，Lambda 按 `createdAt`（缺失时用 `date`）降序整理结果，并返回：

```json
{
  "events": [],
  "complete": true,
  "debug": {
    "eventCount": 0,
    "pageCount": 1
  }
}
```

前端只接受 `complete: true` 且 `events` 为数组的响应。后续页失败或旧后端返回不完整协议时，页面显示读取错误，不会用部分数据生成统计或空态。路径中的用户 ID 仍必须与 Cognito 身份中的 `sub` 一致。

## 资源边界

Lambda 的 CloudFormation 超时设为 10 秒，以容纳少量连续查询页。接口在一次请求内返回完整历史，保证图表和搜索语义准确；渲染侧继续使用既有的有界分页：个人时间轴每页 10 条，事件管理每页 20 条，因此不会同时挂载全部事件卡片。

如果真实用户历史增长到无法在 10 秒内完整读取，应在新的版本化接口中引入服务端分页和独立汇总数据。当前客户端不会对不完整结果做静默回退。

## 验证

- Lambda 单元测试覆盖三页读取、带游标的空中间页、单页空结果、跨用户拒绝及后续页失败。
- API schema、集成和契约测试要求 `complete: true`；超时回归确认缺少 `cancel()` 的适配器不会覆盖原始 TIMEOUT 错误。
- 个人页、事件管理及分页组件 4 个文件共 67 项测试通过。
- 完整单元测试 89 个文件、1266 项通过；隔离生产构建通过。
- Playwright 在开发/生产、390/1440px 四组环境中验证 25 条历史：时间轴为 10/10/5，事件管理为 20/5，搜索可命中跨页记录，不完整响应被拒绝。
