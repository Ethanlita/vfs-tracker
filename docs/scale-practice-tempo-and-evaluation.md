# 音阶练习：速度、检测与整句判定

本文说明 `ScalePractice` 的节拍速度、基频采样和判定逻辑。结果来源与结束行为见[音阶练习结果与结束行为](scale-practice-results.md)。

## 修复的问题

1. **16 拍模式速度过快、经常判不对。** 旧版 `planBeatSchedule` 规定"一轮最多 8 个四分音符（4.8 秒）"。拍数超过 8 时，它会自动把时值缩成八分或十六分音符：九度回转每音只有 300 ms，16 分音符版只有 150 ms。判定要求 `min(250, 0.6 × 拍长)`，即 180 ms 或 90 ms。同时旧版有三处问题：
   - 每拍的帧按名义时间切窗，没有延迟补偿；
   - 用整拍中位数判断偏高或偏低；
   - 设备延迟和"听到再跟唱"的反应时间会让上一个音的残留占据拍窗的大半，结果被误判为偏高、偏低或不稳定。
2. **练习途中音高轨迹停止绘制。** 旧版有两处配合出错：
   - 轨迹点数上限是 320，超出后用 `shift()` 滚动，所以点数一直停在 320；
   - 序列化缓存以"点数"为键，点数恒定后一直返回旧字符串。

   旧版检测循环由 `requestAnimationFrame` 驱动，在 120 Hz 屏幕上约 2.7 秒有声就会填满 320 个点，所以轨迹常在一轮中途冻结。

## 速度（BPM）

- 每个模式在 `src/config/scaleModes.json` 中必须声明两个字段。缺少或非法时，`planBeatSchedule` 会抛错。
  - `defaultBpm`：默认速度，按四分音符计（♩ = BPM），取值 40–160；
  - `noteValue`：时间线上"一拍"的时值，取 `quarter`、`eighth` 或 `sixteenth`。
- 每拍时长 = `60000 / BPM × 时值倍数`（四分音符为 1，八分为 0.5，十六分为 0.25）。时间线补空拍到 4 的整数倍，不再为了总时长压缩时值。
- 用户可以在设置页用滑块调整速度，每个模式单独记忆，存放在 localStorage 的 `vfs-tracker:scale-practice:bpm-by-mode`。存储不可用时只是不记忆，仍使用模式默认速度。
- 默认值：
  - 除下面一项外，所有模式都是四分音符、100 BPM（每音 600 ms）。其中七音模式一轮 12 拍（7.2 秒）。
  - 九度回转的末尾空拍从 5 拍改为 1 拍，一轮共 12 拍。
  - 16 分音符版为十六分音符、80 BPM（每音 187.5 ms）。

## 检测循环

基频检测改用 `setInterval(16 ms)` 驱动（`PITCH_FRAME_INTERVAL_MS`），不再跟随屏幕刷新率。原因是 60、120、144 Hz 屏幕以及省电模式会让每秒帧数、轨迹点数和评估采样密度各不相同。每帧都带真实时间戳，所有时长都按时间戳计算。

轨迹只记录本轮 `[0, 总时长]` 内的点，所以点数天然不超过"总时长 / 16 ms"，不需要截断，一轮从头到尾完整保留。序列化结果以 `trailVersion` 为缓存键。

## 整句判定（`evaluatePhrase`）

一轮连续采集：每拍只记录实际开始时间，最后一拍之后再采集 350 ms 的尾段，然后进入整句判定。

1. **分析窗口**：从第一个练习音开始前 100 ms，到最后一个练习音结束后 350 ms。能量、清晰度和基频范围（50–2000 Hz）都通过门限的帧才算"有声帧"。
2. **全局延迟估计**：在 −100 ms 到"350 ms + 每音时长"之间以 10 ms 为步长平移目标音阶，取总代价最小的平移量。代价规则：
   - 落在某个音区间内的帧，取 `min(|偏差|, 300 cents)`；
   - 早于第一个音的有声帧，记 150；
   - 晚于最后一个音的帧不计代价。最后一个音自然拖长不能把延迟估大。

   估出的值包含设备延迟、人的反应时间和换音时的滑音（它衡量的是音高真正到位的时刻），因此不需要事先知道设备延迟。浏览器报告的 `outputLatency`、`baseLatency` 和输入 `latency` 各浏览器支持不一，蓝牙设备也常低报，所以只显示在诊断面板里，不参与判定。

   搜索范围比允许的延迟多出一个音长，是为了让"晚一整拍"能被估出来。估计值超过上限时整句判为跟唱太晚，见下文。
3. **换音点对齐**：以全局延迟为中心，每个换音点可以再浮动 `min(150 ms, 0.45 × 每音时长)`，绝对偏移不超出 −100…+350 ms。用动态规划求"每帧与所属音偏差"总和最小的切分，无声帧不计代价。上一个音的残留和滑音过渡会归给上一个音。

   第一个音之前、最后一个音之后的有声帧不属于任何练习音，每帧按偏差恰好等于容差（75 cents）计代价。中间的换音点两侧都是练习音，帧总要归给其中一个；首尾两端外侧却没有音。如果外侧不计代价，真人演唱每帧总有几 cents 偏差，首尾音每多收一帧都只会增加总代价，对齐就会把它们裁到搜索窗口最内侧，最多丢掉 0.45 个音长。现在首尾音会收下偏差小于容差的帧；明显唱偏的帧和无声帧仍留在外面，所以真正唱短、唱偏的首尾音照样判失败。

   2026-11-10 修复前，16 分音符 120 BPM 以上稍有抖动，首音或末音就只剩 32–48 ms，被误判为"没有唱到位"。
4. **逐音判定**：每段有声帧的中位数偏差必须在 ±75 cents 内，否则报"不够高"或"不够低"；没有有声帧时报"未检测到"。之后按每音时长选择判定方式（`resolveJudgeRegime`）：
   - **稳定保持**：`0.5 × 每音时长 ≥ 200 ms`（即每音至少 400 ms）时，要求在容差内连续保持 200 ms。这个要求固定为 200 ms，不随速度变慢而变长；
   - **只看音高走势**：每音更短时，只要求在容差内停留 `max(60 ms, 30% × 每音时长)`。

   两种方式衡量的是同一个量：每个音在 ±75 cents 内连续保持的最长时长，区别只在要求多长。设置页会实时显示当前速度下的判定方式。

   | 模式与速度（♩） | 每音时长 | 判定方式 | 要求时长 |
   |---|---|---|---|
   | 四分音符模式 40–150 BPM | 1500–400 ms | 稳定保持 | 200 ms |
   | 四分音符模式 160 BPM | 375 ms | 只看走势 | 113 ms |
   | 16 分音符版 80 BPM | 187.5 ms | 只看走势 | 60 ms |

   2026-11-07 起由「0.6 × 每音时长 ≥ 250 ms，要求 250 ms」放宽为现行规则：250 ms 对真人演唱偏严，切换点也从约 417 ms 移到 400 ms。
5. **切入过早**：只检查"第一个练习音开始 − 100 ms"之前的帧。在允许范围内的轻微抢拍不算切入过早。

## 跟唱太晚

全局延迟估计超过 `350 ms + min(150 ms, 0.45 × 每音时长)`（`resolveLateLimitMs`）时，整句判为跟唱太晚（`failedNote.type = 'late'`），不再逐音判定。提示为"跟唱慢了约 N ms：请和系统播放的目标音同时唱；蓝牙耳机延迟较大，可换用有线耳机"。

上限的含义：换音点最晚只能放在名义时间 + 350 ms，再往后的错位只能靠换音点浮动吸收；超过两者之和，对齐已经无法把每个音放回它自己的时间段。

| 每音时长 | 上限 |
|---|---|
| ≥ 333 ms（四分音符模式 40–160 BPM 都在此列） | 500 ms |
| 187.5 ms（16 分音符 80 BPM） | 约 434 ms |
| 93.75 ms（16 分音符 160 BPM） | 约 392 ms |

估计值包含滑音时间：晚 400 ms 且每个音有 60 ms 滑音，会估为约 460 ms。

2026-11-10 之前并没有真正的延迟上限。延迟搜索只到 350 ms，更晚的部分靠每个音的中位数和稳定时长容忍：每音 600 ms 时晚 550 ms 仍能通过。"晚一整拍不通过"只是因为末音被裁短而碰巧失败：每音 400 ms 时晚 400 ms 就会误判为"保持不足"，每音 1500 ms 时晚多少都能通过。

## 诊断面板

"上一轮判定"区块显示以下内容：
- 判定方式、每音要求时长、估计的总延迟、是否通过；
- 每个音的中位偏差、稳定时长和有声帧数（判为跟唱太晚时不逐音判定，这部分为空）；
- 浏览器报告的设备延迟，仅供参考。

## 测试

- `tests/unit/utils/scalePracticeEval.test.js`：
  - 判定方式切换点（400 ms）与慢速时要求不变长；
  - 延迟估计：准时、晚 200 ms、晚一整拍、尾音拖长、无声；
  - 两种判定方式下的通过与各类失败，包括保持约 220 ms 可以通过；
  - 首尾音边界：16 分音符 80/140/160 BPM 的九音音型，在音高准确、每帧抖动或固定偏差、不同采样相位与延迟下通过，且首尾音保留整个音长（最多因采样相位少两帧）；四分音符每音 400 ms 同样保留；末音之后滑走的帧不计入。负例：首尾音唱短、唱偏或没唱出来仍判失败；
  - 跟唱太晚：上限取值、晚一整拍判为 late、上限以内（含滑音）通过、慢速 1500 ms 与 16 分音符 80 BPM 两侧的边界。
- `tests/unit/utils/scaleModes.test.js`：BPM 与时值换算、补拍、配置校验、所有内置模式的默认速度，以及 BPM 存储读写与损坏数据。
- `tests/unit/components/ScalePractice.results.test.jsx`：
  - 速度滑块、判定方式提示与持久化；
  - 用户速度传入整句判定；
  - 跟唱太晚的提示文案，本轮按失败处理；
  - 长轮次轨迹在 320 点之后仍继续增长。这条回归测试在旧的"截断 + 按点数缓存"实现下会失败；
  - 「再来一次」的三条路径，见[音阶练习结果与结束行为](scale-practice-results.md)。
- `tests/e2e/scale-practice-synthetic-voice.spec.js`：用振荡器替代麦克风，按页面拍号整体晚 220 ms "跟唱"。
  - 每音 600 ms 通过稳定保持判定，估计延迟落在 150–350 ms 之间，最后一拍时轨迹已画到右端 80% 以后；
  - 九度回转调到 160 BPM 后，切换为只看音高走势并通过；
  - 练完一轮后点「再来一次」，不经过耳机检测与校准直接回到设置页，再练一轮仍通过；
  - 设置页和结果页无横向溢出。

合成正弦波只能证明算法与时序链路是通的，不代表真实人声和真实麦克风的声学准确性。真机验收仍需单独进行。
